# Validation and performance

This document records how vk_oidn was validated and measured, with all the numbers obtained
during its development, so the results can be reproduced and regressions detected. How the
library works is described in [architecture.md](architecture.md).

## Test images

The images are synthetic, generated by [`tests/scripts/gen_images.py`](../tests/scripts/gen_images.py):
a lit checkerboard with a sphere and a bright spot, rendered with Monte Carlo-like noise (average
of 4 exponentially distributed samples per pixel with rare fireflies), plus noise-free albedo and
normal images. Three sizes were used: 333x197 (odd size, exercises partial tiles and borders),
1920x1080 and 3840x2160.

```
python tests/scripts/gen_images.py images/odd 333 197
python tests/scripts/gen_images.py images/hd 1920 1080
python tests/scripts/gen_images.py images/4k 3840 2160
```

## Accuracy metric

The same metric as OIDN's `oidnDenoise -r`: for every channel value, the relative error is
`|expect - actual| / (|expect| + |actual| + 0.01)`. A test passes if the average relative error
(`avgerror`) is at most 0.003 (0.05 for normal filtering) and there is no outlier (a value with an
absolute error above 0.02 *and* a relative error above 0.05).

The reference is always the output of the OIDN 2.5.1 **CPU** device for the same configuration.
On top of the metric, outputs were compared **bit for bit** between implementations that should
be identical (e.g. vk_oidn and the OIDN fork running the same kernels).

### Issues found and fixed during validation

| Issue | Symptom | Cause | Fix |
|-------|---------|-------|-----|
| Output biased on AMD | avgerror ~0.004 instead of ~0.0003, image 1% darker | the driver rounds FP32 → FP16 conversions toward zero by default | request round-to-nearest-even and FP16 denormal preservation (SPIR-V float controls) in all kernels |
| FP16 images wrong on AMD | avgerror 0.08 with half input images | 16-bit loads from addresses that are not 4-byte aligned (6-byte RGB pixels) returned wrong data | load FP16 pixels with aligned 32-bit loads |
| FP16 storage image output | avgerror 0.00037 instead of 0.00034 | the rounding of the storage image format conversion is implementation-defined | round to FP16 in the shader when the output view format is FP16 |
| Crash at process exit | segmentation fault after denoising with a progress callback | destroying the global `VkInstance` from a static destructor during DLL unload | the library-global instance of the OIDN fork is never destroyed |
| Fresh clones of the fork | weights submodule not found | relative submodule URL | absolute URL |
| Crash on lavapipe (Mesa 25.2) | segmentation fault with a fixed input scale or LDR input | without autoexposure the scale pointer is 0, and the driver performs the load inside the untaken uniform branch | the kernels load the scale from an always valid address, then select it (bit-identical outputs) |

The KHR cooperative matrix path also produced wrong results on the AMD integrated GPU
(RDNA2, no matrix hardware); cooperative matrices are therefore enabled by default only on NVIDIA
GPUs, and other GPUs use the fallback kernel, which passes all tests on the AMD GPU.

## Performance

### Method

- **OIDN fork and CUDA**: `oidnBenchmark -d <device> -r "RT.hdr_alb_nrm.*"` (wall-clock time per
  image with device buffers, after warm-up), `-q fast` for the fast quality.
- **vk_oidn**: `vk_oidn_denoise_test ... -n 50`, which records 50 `cmdDenoise` calls in one
  command buffer between two GPU timestamps and reports the average GPU time per image.
- **Per-layer times**: OIDN's microbenchmark build (`OIDN_MICROBENCH`) for the fork, and
  `VK_OIDN_PROFILE=1` for vk_oidn (GPU timestamps around each dispatch of the first tile).

All numbers are for the `hdr + albedo + normal` model on the RTX PRO 4500 Blackwell. 3840x2160 is
processed in 2 tiles (OIDN's default maximum of 2160x2160 pixels per tile).

### Final results

| Resolution | Quality | OIDN 2.5.1 CUDA | OIDN fork, GLSL | OIDN fork, Slang | vk_oidn, no sub-pixel | **vk_oidn** |
|------------|---------|-----------------|-----------------|------------------|-----------------------|-------------|
| 1280x720   | high    | 3.50 ms         | 3.67 ms         | 3.43 ms          |                       |             |
| 1920x1080  | high    | 8.10 ms         | 8.12 ms         | 7.50 ms          | 7.29 ms               | **6.72 ms** |
| 3840x2160  | high    | 34.65 ms        | 33.66 ms        | 30.72 ms         | 30.22 ms              | **27.83 ms** |
| 1280x720   | fast    | 2.36 ms         | 1.88 ms         | 1.90 ms          |                       |             |
| 1920x1080  | fast    | 5.55 ms         | 4.14 ms         | 4.17 ms          | 3.96 ms               | **3.65 ms** |
| 3840x2160  | fast    | 23.41 ms        | 16.50 ms        | 16.50 ms         | 16.03 ms              | **14.63 ms** |

vk_oidn is 1.2x (high) to 1.6x (fast) faster than OIDN's CUDA backend on this GPU. Without the
sub-pixel decomposition it runs the same kernels as the fork and is slightly faster because
everything is recorded in the application's command buffer, with no host-side overhead. Storage
image views instead of buffers do not change the time (7.39 ms vs 7.31 ms before the sub-pixel
decomposition).

Memory (scratch + weights) for 1920x1080: 384 MB (base network), 518 MB (large network),
256 MB (small network); 3840x2160 in 2 tiles: 799 MB.

### Laptop results (RTX 3500 Ada Generation)

Balanced power plan. Builds: vk_oidn with Visual Studio 2026 (MSVC 19.51), Slang 2026.17; the OIDN

### Experiment: `VK_NV_cooperative_matrix2`

NVIDIA's cooperative matrix 2 extension (all features supported on this GPU: workgroup-scope
matrices up to 1024 per dimension with M32/N16/K16 granularity for 128 invocations, tensor
addressing, block loads) was tried with a different kernel design
(`shaders/experimental/conv_cm2.comp`, enabled with `VK_OIDN_CM2=1`): one workgroup-scope
accumulator per BM pixels of a row and all output channels, A matrices loaded directly from the
input rows with clamped tensor addressing (which implements the zero padding), no explicit shared
memory. It is used for the layers without pooling/upsampling.

| BM (pixels) | BK (channels) | Total time | dec_conv2b | dec_conv1b |
|-------------|---------------|------------|------------|------------|
| KHR kernel  | –             | **7.11 ms** | 0.509 ms  | 0.943 ms   |
| 32          | 32            | 9.07 ms    | 0.607 ms   | 1.762 ms   |
| 64          | 32            | 9.43 ms    | 0.515 ms   | 1.518 ms   |
| 32          | 64            | 8.95 ms    | 0.633 ms   | 1.670 ms   |
| 64          | 64            | 9.49 ms    | 0.589 ms   | 1.515 ms   |
| 128         | 32            | 10.38 ms   | 1.541 ms   | 1.468 ms   |
| 256         | 32            | 15.02 ms   | 1.549 ms   | 3.248 ms   |

The output is correct (avgerror 0.000340), but this design is 25-30% slower than the tuned
`VK_KHR_cooperative_matrix` kernel, so it is not used by default. Likely reasons: the 3 horizontal
taps reload overlapping input data instead of reusing it, and many small workgroup-scope
multiply-adds each go through the driver's internal staging. Possible improvements: load the 3
taps as one wider K (overlapping rows, with explicit handling of the image borders), larger K per
multiply-add, or using cooperative matrix 2 only for the matrix multiplications while keeping
the explicit shared memory tiling. Note that Slang's tensor addressing currently requires
descriptor-bound buffers, which is why this kernel is written in GLSL.

### Sub-pixel decomposition of the upsampling layers

The four decoder layers `dec_conv*a` convolve a 2x nearest-upsampled tensor (concatenated with a
skip connection). A 3x3 convolution of an upsampled tensor is exactly four 2x2 convolutions of the
low-resolution tensor, one per output phase (row parity, column parity), with combined weights
(along each axis: phase 0 uses offsets {-1, 0} with weights {w0, w1 + w2}, phase 1 offsets
{0, +1} with {w0 + w1, w2}). This removes 56% of the multiply-adds of the upsampled source, which
is most of the work of these layers (e.g. 64 of the 80 input channels of `dec_conv1a`).

In the kernel (`convCoopMatUp`), each 16-pixel matrix fragment holds output pixels of a single
phase (every other pixel of a row), so all its rows use the same combined weights; the
low-resolution source is read from a half-resolution shared memory tile, and the skip connection
with stride-2 rows from the full-resolution tile.

The first version gave each subgroup the 4 phases of 2 rows. It was **slower** (7.79 ms vs
7.31 ms): each weight tile was used by a single fragment, so the kernel became bound by the weight
loads (the original kernel reuses each weight tile for 4 fragments). Giving each subgroup one
phase (4 rows of the same parity) restores the reuse and gives the speedup above: 1.20-1.40x on
the upsampling layers, about 8% overall (1080p high: 7.29 → 6.72 ms, fast: 3.96 → 3.65 ms;
4K high: 30.22 → 27.83 ms, fast: 16.03 → 14.63 ms).

### Tensor core peak, and an experiment with cooperative vectors (`VK_NV_cooperative_vector`)

How far are the kernels from the hardware limit, and could cooperative vectors, the newer
SPIR-V matrix-vector instructions for neural shading, be faster? The micro-benchmarks in
[`tests/microbench`](../tests/microbench) measure this on the RTX PRO 4500 Blackwell
(driver 617.42, Vulkan SDK 1.4.363).

**Tensor core peak** (`VK_KHR_cooperative_matrix`, register-only multiply-add chains, best of 1 to
8 independent chains per subgroup):

| Inputs → accumulator | Peak |
|----------------------|------|
| FP16 → FP16          | 203 TFLOPS |
| FP16 → FP32          | 200 TFLOPS |
| FP8 (E4M3) → FP16    | 399 TFLOPS |
| FP8 (E4M3) → FP32    | 394 TFLOPS |
| INT8 → INT32         | 454 TOPS |

The high quality network does 565 GFLOP per 1920x1088 frame (with padded channels), so 6.36 ms is
an average of 89 TFLOPS: **about 45% of the FP16 peak** (the largest layer reaches 98 TFLOPS,
49%). The kernels are limited by data movement (loading the activation tiles and weight fragments
of each multiply-add from shared and global memory), not by the tensor core math. Register use
matters too: in the peak test, 6 or 8 independent FP16 chains per subgroup reach only about
100 TFLOPS (fewer resident warps).

**Cooperative vectors** (FP16, matrices converted to the inferencing-optimal layout with
`vkCmdConvertCooperativeVectorMatrixNV`). The driver reports up to 1024 components, with FP16, INT8
and FP8 matrices. Slang supports them (`CoopVec`, `coopVecMatMulAdd` with pointers), so writing
SPIR-V by hand is not needed; the benchmark kernels use GLSL (`GL_NV_cooperative_vector`).

| Test | Time | Throughput |
|------|------|------------|
| Matrix-vector chain 32x32 / 64x64 / 128x128 (input in registers) | - | 135 / 86 / 82 TFLOPS |
| 3x3 convolution 64 → 64 channels, 1920x1088 (154 GFLOP), 9 products of 64x64 per pixel | 38.5 ms | 4.0 TFLOPS |
| same, 3 products of 64x192 per pixel (3 adjacent input pixels are contiguous) | 42.8 ms | 3.6 TFLOPS |
| same, input vectors computed instead of loaded (products only), 9 / 3 products | 1.18 / 0.94 ms | 131 / 165 TFLOPS |
| same, products replaced by the loaded vectors (memory traffic only) | 1.71 ms | - |
| vk_oidn FP16 kernel on comparable 64-channel layers (`dec_conv2b`, `dec_conv1b`) | ≈2.0 ms | 76-77 TFLOPS |

The products alone and the memory traffic alone are both fast, but together the convolution is
about 20 times slower than vk_oidn's kernel. Changing the workgroup shape, using a single matrix,
removing the bias, not unrolling the taps, or adding arithmetic between the load and the product
does not change it. The fast path of cooperative vectors seems to need inputs computed in
registers, as in per-pixel MLPs (neural materials, texture decompression); a convolution, whose
inputs are neighboring pixels in memory, does not fit it with this driver. Even in the
products-only case, the throughput (131-165 TFLOPS) would leave little room over a better
cooperative matrix kernel.

**Conclusion:** cooperative vectors are not a way to speed up vk_oidn. The headroom is in data
movement (up to about 2x to the FP16 peak) and in FP8 (2x the math peak and half the bytes moved).

## Ideas for further speedups

- Less data movement per multiply-add in the FP16 kernels (the measured peak is about twice the
  current average): larger register tiles per subgroup with FP16 accumulation (fewer registers),
  larger K chunks (32 channels), weights staged in shared memory.
- FP8 (E4M3) cooperative matrices: 2x the FP16 peak and half the bytes for weights and activations.
  The FP16-trained weights would need a quantization accuracy analysis (per-channel scales), and
  probably quantization-aware fine-tuning with the Open Image Denoise training scripts.
